# Git view implementation inventory

This task snapshot is the working contract for the opt-in Git layout. The first implementation slice keeps existing actions on their existing components and handlers; it does not claim the full redesign is complete.

Renderer long Git actions retain scoped idempotency keys when the start response is lost, then reuse them on explicit retry; accepted work waits for terminal event or persisted result before clearing busy state. Pull/push/force-push and tag network writes use the audited mutation wrapper; fetch records an action without a write audit. Publish uses the provider review operation path. |

## Existing action entry-point index

This index records the concrete UI entry points found in the existing Git shell. It is a route map, not a claim that every possible result variant has a dedicated view. Buttons and context-menu picks dispatch through the listed Git UI store or existing provider/file API. No Git-specific keyboard shortcut was found in the inspected Git shell; the keyboard bindings present are picker/menu navigation, graph selection, form submission and focus controls.

| Entry point and actions | Dispatch and guard | Result/error surface | New-view destination |
| --- | --- | --- | --- |
| Shared toolbar: refresh, fetch, pull strategy, push, publish, lazygit; root picker; conflict resolution | `GitPane.vue` → `git-ui` store; toolbar disables actions for pending/busy operations; publish/provider guards remain in the existing PR flow | Shared operation card in History/Changes/Review; standard notification; refresh/read errors stay in store/UI state | Shared header/action area |
| Branch list row/menu: checkout local/remote, create from, rename, delete local/remote, merge/rebase, create PR; branch refresh and compare | `GitBranchesTab.vue` / `BranchTreePane.vue` events → `git-ui` store; manager validates branch state and confirmations; provider PR retains provider permission checks | Git operation result/notification; branch and compare panes show read status | More → Branches; History picker itself is read-only |

A manual visual pass is still needed for discoverability, focus, and narrow-window presentation; this table does not substitute for that acceptance step.

| History query | Either context | Electron or remote/web renderer | Selected ref, search and graph reads are scoped by profile/workspace/root; picker selection never changes checkout. | `gitLoadGraph` reads a single ref or distinct all-refs/HEAD query. Stale root/profile responses are ignored. |

The picker currently shares the legacy branch-history component/data path. Favorites and recent refs persist in browser storage scoped by profile/workspace/root. Selected History ref and commit search are kept by the Git UI store scoped by profile/workspace/root. Graph, branch, tag, compare, commit diff, and working diff results have request/context guards; post-action preview refreshes capture their originating root/path/scope and cannot replace another root's selection. Tag-list failures render an inline alert. Compact History keeps commit text search by message, author, or hash and reports no-match state. `HEAD` and all-refs are distinct graph queries. Saved refs remain visible during loading, deleted refs are explained, and missing refs are pruned after completed reads; loading/error transitions are guarded. Table entries describe implemented transport and scope behavior; human confirmation of actual view presentation remains pending.

The narrow Changes diff also provides the layer label, stage/unstage file and hunk actions, and Commit staged. These controls use the same store APIs as desktop Changes.

The shared Git toolbar includes a keyboard-focusable native Details disclosure for the complete active repository path and working branch. The compact branch chip remains unchanged; long paths wrap inside the disclosure panel.

## Remaining verification boundaries

- Human visual verification remains with the user: the plan explicitly keeps Electron and the dev server out of agent verification. No app process has been launched.
- The existing classic tabs remain the destination for specialized branch, stash, worktree, bulk, and conflict tools; More routing prioritizes these destinations over the selected new view. Verify each via the More selector in the user's visual pass.
- The native ref select provides keyboard search/selection/escape behavior; a user visual pass should still check long refs, a large branch list, and narrow-window sizing.
- Latest recorded verification (2026-10-21): current backend at four workers passes 224 files / 5,468 tests (7 skipped); current `npm run typecheck` and `npm run lint` pass (0 errors / 4,685 warnings; Prettier clean). Full UI has 214 passing files / 3,072 passing tests and one transport reconnect timing failure; the failed test passes when run alone. See `JUDGE_TODO.md` for continuation evidence and user-owned manual review status.
- The runtime operation coverage includes long fetch/pull/push/force-push, remote branch deletion, merge/rebase (including fetch-first), and network-backed tag push/delete actions. Remote slot routes are profile/session guarded; slot-aware merge/rebase, tag and remote branch mutation routes validate their payload schemas before dispatch. `merge-into-base` is a local sibling-worktree operation and remains synchronous.
